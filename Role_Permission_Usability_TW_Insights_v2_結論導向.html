1 V / M / R 權限定義與連動關係
3 個痛點

受測者對 V / M / R 的定義與連動方式感到困惑，多數人期待勾選較高的權限時，較低的權限應該自動被包含進來。

權限的定義與心智模型不明，尤其對「Run」疑惑
IT-1IT-2CSO-1CSO-2
命中100%P0Spec
情境 / Context 受測者大概可以猜到 View=看、Modify=可修改，可理解 Run 代表「執行」，但不清楚為什麼需要將「修改設定 (Modify)」與「執行動作 (Run)」拆分得如此細碎。他們認為這兩者是高度重疊的。加上實際操作中 Run 的語意在不同頁面又不一致：在 Topology 上是「產 PDF」、在 Device 內頁是「Live tool / Reboot」、在某些設定頁卻又看不到對應動作。整個任務過程都被「Run 到底代表什麼」干擾，並讓使用者開始懷疑自己對整套權限模型的理解。
證據 · Evidence
  • Modify 有包含 Run，所以會根據功能同時勾選 Modify 跟 Run。IT-1
  • Modify 完之後可不可以執行它，又獨立拆開來那也很刻意 — 明明就是連貫動作。CSO-2
  • 無法理解 Run 的意思，因為 NCC 上都是 Monitor 跟 Config。CSO-2
  • 問卷 Q4：4 人對 Run 的一句話描述全都不同（執行 / 可執行操作按鈕 / Live tool / ?）。
建議 · recommendation
  • Spec 層級：先釐清 Run 範圍邊界（物件層級執行？頁面層級 Live tool 集合？）寫進 PRD。
  • 對齊 Live tool：考慮把 Run 直接映射為「Live tool / Execute」，回到 NCC 既有世界觀（Monitor / Config / Live tool）— CSO-1 訪談中本能地以 Live tool 解釋 Run，這條路徑學習成本最低。
  • 無執行物件頁面隱藏 Run 欄位：避免使用者陷入猜謎迴圈。
View / Modify / Run 連動關係不明
IT-1IT-2CSO-1CSO-2

情境 / Context 在多個情境（特別是情境 1、2）受測者面對 View / Modify / Run 三欄勾選時，會猶豫該勾哪一個，常見的處理是「不確定就三個都勾」。當意識到實際上有「只勾 Run 但 View 是 disable」這種組合時，受測者會明顯困惑：「沒辦法 View 怎麼 Run？」這個 mental model 衝突在每次切換 permission 都會再次出現，是累積性的疲勞。

建議 · recommendation
  • 產品決策三選一：(A) 維持三者獨立 / (B) 階層包含（View ⊆ Modify ⊆ Run）/ (C) 各自獨立但 UI 強制連動。建議採 B，貼近 IT 既有 NTFS / AD 心智模型。
  • 若維持獨立：必須在介面上明確標示「三者獨立」說明，並用 tooltip 或 helper 文案教育。
  • 禁用無效組合：勾 Run 時自動勾 View 並 disable，而不是放任使用者勾出無意義組合。

3 Template 策略與過度授權風險
量化驗證組

受測者會主動使用 Template 作為起點，但現有預設範本並未針對客戶情境設計，套用後需花大量時間調整，也容易造成過度授權。

現有預設範本屬於「系統層級」的劃分，與真實客戶需求分工「任務 / 職能層級」劃分存在落差
IT-1IT-2CSO-1CSO-2
命中100%P0Spec+UX
情境 / Context 目前系統提供的預設範本（Viewer、Admin）是以通用角色為基準設計，並未針對 MRD 中的新客戶需求重新調整。受測者套用後，面對大量已被帶入的不相關權限，不知道哪些需要移除、也不知道從哪裡開始，移除成本極高。情境 2 中使用 Viewer 的受測者平均帶入 131 個多餘權限，精準度僅 8.4%；情境 3 中使用 Admin 的 IT-1 需從 426 個中大量刪減至 43 個。在高壓或時間緊的情況下，使用者可能直接放棄修改，導致過度授權的資安風險。
量化證據 · Quantitative Evidence
  • 情境 2 · Viewer template：平均命中率 75.0%，精準度 8.4%，平均額外帶入 131 個權限
  • 情境 3 · Admin template：命中率 72.7%，精準度 93.0%，需從 426 個中大量刪減

建議 · Recommendation
  • 套用前預覽：顯示 template 包含的總權限數、各 category 摘要、適用情境說明。
  • 套用後 Diff 提示：明確顯示「新增了哪些權限」「哪些 category 超出情境範圍」。
  • 情境化 Template：以實際客戶需求為基準，建立更細粒度的 scenario-based template 取代通用 Admin / Viewer。

情境 / Context 「Show Config Only」定位是「暫時篩選、只看目前已勾選的項目」。但受測者指出，這是暫時性檢查輔助，並非整體評估的解決方案——使用者核心需求是確認「有沒有遺漏」，這個功能只能看到「已勾的部分」，無法幫助確認還有哪些應該勾但尚未勾選。CSO-2 指出比較適合在「Role 建立後回頭檢視 / 編輯」時使用。
證據 · Evidence
  • 我原本以為它會去跟我上面剛剛選的 template 做 diff 比較…從 template 找到跟 template 的差異。CSO-1
  • 試了幾次看不出來功能是什麼…可能因為是 toggle 樣式，沒有讓人覺得點擊後會篩選下方的資料。CSO-2
建議 · recommendation
  • 視覺更換：toggle → 篩選器 icon（funnel）或標準 chip filter。
  • Wording 改寫：「Show config only」→「Show only selected」。
  • 使用情境曝光：在 edit role 流程中強化此功能曝光，初次設定階段可隱藏或降低視覺權重。
